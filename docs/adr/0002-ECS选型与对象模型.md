# ADR 0002：ECS 选型与对象模型

- 日期：2026-11-18
- 状态：Accepted
- 关联：README §5.1、§9.3、§9.4、§9.5

## 背景

需要一个数据导向的实体组件系统，支撑 10k 实体的变换更新、场景存取与编辑器 Inspector。
原型期的 `mir-ecs` 是 `HashMap<TypeId, HashMap<Entity, Box<dyn Any>>>`，无查询/调度/变更检测，
`Entity` 是裸 `u64` 无世代标记。需要决定 M3 采用的实现与对象模型风格。

## 决策

1. **内部采用 `hecs`**，对外封装稳定的 `World` / `Query` / `System` API；不在引擎内自研 ECS 内核。
2. **资源（Resource）与组件分离**；调度顺序由 `Schedule` 决定，变更检测用版本号记录 Added/Changed。
3. **世代句柄**：实体/对象引用使用带世代的句柄（原型期裸 `u64` 在 M3 迁移），避免回收 ID 产生悬垂句柄。
4. **Actor 是外观而非基类**：Actor 元数据（名称、层级、反射类型）作为组件；运行数据（Transform、Renderable）进 ECS；
   行为通过组件与 trait 组合，用 `enum`/泛型表达类型差异，不模拟 UE 的 `UObject` 继承树。
5. **对象模型 Rust 优先**（§9.3）：`#[derive(Reflect)]` 编译期生成 `TypeInfo` 注册进 `TypeRegistry`；
   无追踪 GC，显式 `destroy`；禁止运行时代码生成。
6. **渲染解耦**：`mir-render` 不依赖 `mir-scene`；每帧 `extract` 阶段把 ECS 数据转成纯帧数据（相机、光源、实例、材质）。

## M3 落地补记（2026-11-26）

- `mir-ecs` 已切换为 `hecs 0.10` 门面：实体为世代句柄 newtype，组件访问通过 `Ref`/`Mut` 守卫，
  查询以回调形式暴露，避免 `QueryBorrow` 的第三方生命周期泄漏到公共 API。
- `Resource` 与组件存储分离；`ChangeTracker` 按组件类型记录 Added/Changed 与递增 tick，
  可变访问按保守策略标记为 Changed。
- `mir-scene` 以 `ActorId`（稳定 u64）+ `ActorMeta`/`Parent`/`Children` 组件实现 Actor 外观；
  场景快照只保存稳定 ID，不保存 ECS 内部实体编号。
- 验证：`cargo test --workspace` 全绿；10k Actor 世界矩阵基准扁平 0.10 ms / 纵深 0.36 ms；
  世代句柄失效与父子循环均有失败用例。

## 替代方案

- **自研 archetype ECS**：可控性最高，但查询调度/并行迭代工程量巨大，偏离「游戏引擎功能优先」目标。
- **bevy_ecs**：功能强但生态绑定重、API 面积大，与保留自身 `Schedule` 语义的规划冲突。
- **沿用原型 `HashMap<TypeId, …>`**：无变更检测与性能保障，`dyn Any` 泛滥违反 §11.2。
- **模拟 UE 的 UObject/继承**：与「Rust 惯用法优先」「clean-room」双重约束冲突。

## 后果

- 正面：查询性能有成熟保障（验收 10k×3 组件 < 1 ms）；世代句柄消除悬垂引用；编译期反射让 Inspector 与序列化共用数据源。
- 负面：引入 `hecs` 依赖并需在 M3 重写原型 API；外部封装层需覆盖 hecs 细节，避免其类型泄漏到公共 API。
- 约束：任何在业务代码里引入 `dyn Any` 或裸 ID 的改动视为评审阻塞项。
