# ADR 0010：Rust-first API 与「不做 1:1 迁移」边界

- 日期：2026-11-18
- 状态：Accepted
- 关联：README §4.2、§5.1、§9.3、§11.2、§11.6

## 背景

Miriya 以 UE 5.8.4 作为行为参考，但必须明确「借鉴」与「复制」的边界，以及 API 设计风格。
若照搬 UE 的 C++ 对象模型与命名，既违背 Rust 惯用法，也可能触及源文件使用与衍生作品风险。

## 决策

1. **clean-room 声明**：不复制、不翻译 UE 源代码；不将 UE 头文件/实现细节作为设计输入；
   仅依据公开文档、API 参考与可观察行为。任何从 UE 源码「移植」的 PR 一律拒绝（§11.6）。
2. **行为对齐而非 1:1 迁移**：对 UE 子系统做近似替代（如ECS→hecs封装、RHI→单一Vulkan、Slate/UMG→自研UI+
   可插拔编辑器后端），在 README §7 记录映射与「近似/替代/不做」状态。
3. **Rust 惯用法优先**：公共 API 使用所有权/借用、newtype、`enum`、trait/泛型、`Result`、迭代器；
   参数用 `&T`/`&mut T`/`impl AsRef`/`Into`，避免 bool 参数与 out 指针；用 newtype/enum 表达领域语义，
   禁止裸 `u32`/`bool` 跨模块传业务概念（§11.2）。
4. **不模拟 C++ 风格**：不建立 `UObject` 继承树、虚表或手写坐标翻转；状态/事件用 `enum`；
   对象用世代句柄 + 所有权管理，无追踪 GC（§9.3）。
5. **类型擦除仅限边界**：`dyn Any`/`Box<dyn Error>` 的滥用只允许在反射、脚本与插件边界；业务路径优先具体类型/泛型。
6. **错误策略**：库用 `thiserror` 定义领域错误，CLI/应用用 `anyhow`；运行时与资产解析禁止 `unwrap/expect/panic!`。
7. **unsafe 约束**：除 FFI/Vulkan/音频/平台 crate 外，crate 级 `#![forbid(unsafe_code)]`；
   unsafe 必须有 `// SAFETY:` 注释与最小化作用域（Vulkan PoC 已遵循，见 RFC 0001）。
8. **许可与合规**：MIT OR Apache-2.0 双许可；依赖经 `cargo-deny` 审核（禁 GPL/未知许可）；
   不使用 UE 商标/Logo/模板内容；`mir-uasset` 等接触 UE 专有格式的功能发布前需合规评审（§11.6）。

## 替代方案

- **1:1 移植 UE 类名与继承体系**：熟悉 UE 的开发者上手快，但与 Rust 风格冲突，且带来源文件使用与衍生作品风险。
- **完全忽略 UE 参考**：失去行为对齐带来的美术/教程生态复用价值。
- **大量 `dyn Trait` 模拟虚表**：牺牲静态类型与性能，违背 Rust-first。

## 后果

- 正面：API 安全、可组合、可静态审查；clean-room 边界清晰，降低合规风险；行为对齐让玩家/开发者能从 UE 经验迁移。
- 负面：UE 背景的开发者需要适应 Rust 所有权与类型风格；「近似替代」意味着某些 UE 特性不会有直接对应物，需在文档中说明差异。
- 约束：PR 评审需同时检查 Rust 惯用法与 clean-room 合规；架构性变更必须先有 ADR/RFC（§11.7）。
