# ADR 0008：物理仅接口，由外部后端实现

- 日期：2026-11-18
- 状态：Accepted
- 关联：README §5.1 规则 8、§9.9

## 背景

物理引擎（宽相/窄相、约束求解、刚体动力学、角色控制器）是独立的复杂领域。
自研或内置第三方求解器都会占用大量本应用于游戏引擎核心功能的工程量。

## 决策

1. **`mir-physics` 只定义契约与引擎侧胶水**，不包含求解器、刚体/碰撞算法或角色控制器；
   不内置 Rapier/PhysX/Chaos 等任何具体实现。
2. **接口范围**：`PhysicsBackend`（世界创建/销毁、`step(FixedStep)`、刚体/碰撞体增删、变换读写、
   raycast/sweep/overlap、接触事件、debug draw、可选序列化）；`BodyId`/`ColliderId` 为世代句柄。
3. **引擎职责**：固定步累加与调用顺序、句柄表、查询转发、Z-up ↔ 后端坐标转换（遵循 ADR 0003，转换只在 interop）、
   调试绘制收集；不实现宽相/窄相/约束求解。
4. **接入方式**：外部后端以 `PhysicsPlugin` 注册（首选 Rust trait，独立 crate）；非 Rust 后端可加可选 C ABI 适配层，
   契约不变。运行时 crate 不得依赖任何具体物理引擎。
5. **内置空后端**：`NullPhysicsBackend` 供 CI/服务器；提供可复用的 `physics-contract` 契约测试套件供后端作者验证。
6. **确定性**：由外部后端声明并测试；引擎只保证固定步与调用顺序一致，不以引擎名义承诺物理确定性。
7. **验收**：mock 后端通过契约测试；外部后端接入示例可运行；引擎侧调度/查询开销 ≤ 0.2 ms（不含求解时间）。

## 替代方案

- **自研求解器**：工程量巨大，偏离核心目标。
- **内置 Rapier**：上手快但与「不内置具体引擎」冲突，且锁定单一实现，替换成本高。
- **完全不做物理层**：场景查询/射线检测等常用能力无统一入口，玩法与工具链难以一致。

## 后果

- 正面：引擎体积与维护面小；后端可插拔、可替换；契约测试保证接入质量；与「Rust 优先/所有权」风格一致。
- 负面：项目初期没有可用物理，任何需要碰撞的玩法必须先接入外部后端；契约设计的完备性需要前期仔细推敲。
- 后续：M6 起草并实现 `PhysicsBackend` 契约与 `NullPhysicsBackend`，v0.4 起接入外部自研后端。
